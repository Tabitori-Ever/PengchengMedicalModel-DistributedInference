2  方法与实验设计

影响结论的两条部署约束（来自集群清单，不在本数据文件内）

  • 诊所（端）Pod 的 CPU limit 为 1500m（1.5 核），医院（边）Pod 为 4 核量级，数据中心节点为 4 核量级——这直接决定“本地执行把 N 份分区串行压在 1.5 核上”的下限。
  • 节点上还混布着其它服务（如调度器、监控、Redis），本次测量未做节点间负载隔离，见第 7 节。

2.2 两种调度策略的执行模型

任务类别协同 vs 本地 的执行差异
计算类协同：把固定的 3 个分区并发派给发起 Pod、数据中心与空闲边缘节点，调度侧并行分摊；本地：发起 Pod 上串行跑完 3 份分区，受该 Pod 的 CPU 配额（clinic 1500m = 1.5 核）限制。
诊断类协同：把「边端前端 → 云端后端」拆成两段流水线，批量越大重叠越充分；本地：发起 Pod 上串行执行完整模型。
通信类协同：数据中心持有分块归属表，开 concurrency 条并行同步流；本地：无中心分块表，单流顺序拉取。
日常类协同：把一次性 Job 并发派发到空闲边缘节点与数据中心（每个 Job 有真实的容器启动开销）；本地：在发起 Pod 内内联执行，无 Job 调度与容器冷启动。
上图左右两栏用同一时间轴直觉对照：协同把关键路径切开，本地把所有环节串起来。

2.3 测量口径

  • 主指标：站点后端墙钟 client_total_ms，即“从站点发出任务到拿到结果”的端到端耗时，含网络与排队。
  • 两种策略的调用形态不同：协同为异步提交 + 轮询，墙钟里包含排队与轮询间隔；本地为一次同步调用，墙钟里不含排队。这是本报告最重要的口径差异，见第 6 节。
  • 统计量：每档给出样本数 n、均值 mean、p50、p95（线性插值分位数），套件级另有成功/失败计数。
  • 重复与种子：每档重复若干次，且每档固定 seed，保证协同与本地在同一档位上产出可逐项比对的结果。
  • 报告只读数据：渲染脚本不重算统计量，直接呈现 JSON 中的聚合值；若某档缺一侧数据则标记为不可比，不做外推。
样本数直接取自数据文件的 overall.<mode>.n；验收线固定为 ≥10%。

本类小结（由数据推导）

  • 整类结论：协同 549.3 ms（n=80） vs 本地 973.4 ms（n=80），协同相对本地 +43.6%（比值 1.77×），判定 达标（验收线 ≥10%）。
  • 逐档极值：增益最大 极重（协同 1,220.3 ms vs 本地 2,951.7 ms，+58.7%）；最小 对照（协同 319.8 ms vs 本地 42.2 ms，-657.9%）。
  • 负载趋势：按各档本地耗时（任务量的代理指标）从小到大排列，协同增益依次为 -657.9% → -4.3% → +35.0% → +47.1% → +58.7%，整体表现随任务量单调上升。说明协同收益主要来自“工作量越大、被摊薄得越充分”。
  • 如实指出协同反而更慢的档位：对照 档：协同 319.8 ms 慢于本地 42.2 ms（-657.9%，协同为本地耗时的 7.58×）；该档算力负载最小，协同新增的编排与分区结果汇聚开销无法被并行收益摊薄，出现“开销淹没收益”。该档参数：仪器数 4 · 行数 512 · 强度 60 · 分区数 3 · …。
  • 调度侧证据：平均调度并行加速比（extra.parallel_speedup）协同 1.89×、本地 0.92×；平均派发墙钟 协同 462.2 ms、本地 1,008.3 ms。协同的调度并行度显著高于本地（本地≈1，即串行），方向与增益一致，说明增益主要来自把关键路径切开，而不是单个任务跑得更快。协同的派发墙钟反而只有本地 0.46×（462.2 ms vs 1,008.3 ms），本类没有出现“编排开销反超”的迹象。

小结中的每个数字都可回溯到上面的对比表与 extra 字段；机制解释是对“数据为何如此”的归因，在缺少 extra 时已标注为推断。

5  正确性校验

校验思路：每一档使用固定 seed，协同与本地拿到完全相同的任务参数（同样的仪器数 / 行数 / 强度 / 分区数 / 病例批量），因此两边应当产出同一组分区 checksum 与同一个 bpCR（诊断概率）。报告只呈现数据文件里真实带有的校验字段；字段缺失时只描述方法，不补数字。

方法（无论数据是否带校验字段都成立）

  • 参数同源：档位参数由套件定义冻结（见第 3 节各表的“参数 / 固定 seed”），调度策略是两侧唯一的自变量。
  • 计算类：逐分区比对 checksum；协同侧的分区结果为基准，本地侧同档位 checksum 应逐项相同。
  • 诊断类：比对 bpCR（bpcr_actual / bpcr_expected）；当期望值为 0/1 标签时按 0.5 二值化后判等。
  • 站点后端的对比视图内含 correctness 列，可直接复核；本报告不重算 checksum。
当前数据文件中未包含 correctness / checksum / bpcr 相关字段，因此本节只描述校验方法，不给出任何一致性数字。如需在报告里展示逐档 checksum 一致性，请在导出 JSON 时补充该字段。

6  口径与假设

口径与假设（必读）

  1. 墙钟口径：主指标 client_total_ms 是站点侧墙钟。协同是“异步提交 + 轮询”，因此其间歇式等待与排队时间计入协同的一方；本地是“一次同步调用”，不含排队。这一不对称对协同是不利的（协同被计入了额外等待），因此本报告的加速比不应被解读为“协同的纯执行更快”。
  2. 计算类：协同把固定的 3 个分区并发派给 3 个节点（发起 Pod / 数据中心 / 空闲边缘节点）；本地在发起 Pod 上串行执行同样 3 份分区。本地一侧受该 Pod 的 CPU 配额限制（诊所 limit = 1.5 核），因此本类的差距很大一部分来自“1.5 核串行”而非模型本身。
  3. 诊断类：协同把「边端前端 → 云端后端」做成两段流水线，批量越大、两段重叠越充分；本地在发起 Pod 上串行跑完整模型，无重叠。
  4. 建模假设通信类：bandwidth_mbps 按每源链路计价。协同由数据中心持有分块归属表，开 concurrency 条并行流；本地无中心分块表，按单流顺序拉取。“协同能开出并行流、本地只能单流”是平台内置模型的建模假设，不是从真实网络测得的结论——真实瓶颈（上行带宽、出口队列、跨机房 RTT）可能显著改变本类的对比结果，欢迎按此假设质疑本节数据。
  5. 日常类：协同把一次性 Job 并发派发到空闲边缘节点与数据中心，每个 Job 带有真实的容器启动开销（约 2–3 s 量级）；本地在 Pod 内内联执行，没有 Job 调度与冷启动。因此本类的胜负高度依赖“作业数 × 启动开销”与“并行收益”的相对大小。
  6. 模拟模型：所有算力与带宽数值都来自平台内置的模拟模型（common/v3_common.py），并非真实医疗数据的吞吐测量；本报告度量的是调度策略的相对差异，不能当作临床吞吐或生产容量规划的依据。
  7. 不做的推断：报告不重算统计量、不填补缺失字段、不做外推；缺数据一律记作“数据不足”，缺一侧的档位一律记作“不可比”。

模型切分点分析（诊断类归因）

诊断任务的协同路径是「边端做前端 → 云端做后端」。切分点决定了中间特征体积与端侧卸下的算力，也就决定了拆分能否划算：中间特征越大、端侧留下的算力越少，拆分越是纯亏。

输入体积（DCE+DWI，float32）= 0.40 MB；端侧完整模型耗时（离线测量）= 263.1 ms。

7  局限与后续工作

  • 单集群 · 单次测量：全部数据来自一套 Kubernetes 集群、每种配置重复有限次；报告未给出置信区间与显著性检验，档位间的轻微差异可能落在测量噪声内。
  • 节点负载未隔离：边缘与数据中心节点上混布着调度器、监控、Redis 等常驻服务，且四类套件是顺序跑的，前一类任务的余温（镜像拉取、缓存、Job 残留）可能影响后一类。严格复现需要在空载节点上逐类单独测量。
  • 协同的绝对时延下限受编排开销约束：异步提交、轮询间隔、跨节点传输与 Job 容器启动构成固定成本；当单档工作量小于该固定成本时，协同必然更慢——这不是策略缺陷，而是适用边界。
