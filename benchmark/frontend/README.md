# benchmark-site frontend（测试与性能对比平台 · 站点前端）

React 18 + TypeScript + Vite 单页站点，对应设计契约 `调度模式与降级-设计方案.md` §6。
独立部署，**不依赖 scheduler 存活**（这是能做降级测试的前提）。

## 构建与开发

```bash
# 依赖（离线机器：直接从既有前端目录复制 node_modules）
cp -r ../../frontend/node_modules ./node_modules

npx tsc --noEmit     # 类型检查
npx vite build       # 产出 dist/（base '/'，后端同源挂载）
npx vite             # 开发服务器 :5174，/api 代理到 http://localhost:8099
npx vite preview     # 预览构建产物 :5175
```

依赖版本与既有前端一致：react/react-dom `^18.3.1`、vite `^5.4.0`、
@vitejs/plugin-react `^4.3.0`、typescript `^5.5.0`、axios `^1.7.0`。
**无图表库**：所有柱状图 / 堆叠图均为手写 SVG + CSS。

### 两条时延口径（别混）

* **任务处理总用时** = Σ 单任务 `client_total_ms`，即大纲里"所有任务处理总用时"。**判定用这条**。
* **阶段墙钟** = 该阶段从第一个任务产生到最后一个任务完成的 makespan，其中包含固定的"
  任务产生窗口"。窗口两遍相同，计进去只会稀释策略差异，所以只作参考。

### 任务保障：失败自动重传（成功率要求 100%）

失败任务会**自动重传**，不再直接判失败：

* 额度：方案声明 `retries`（默认 3 次，即最多 4 次尝试；可在实验配置里改，全局默认见
  `config.attempt_retries`）。子 run 会把方案额度随 `params._retries` 下发，优先于全局默认。
* 退避：每次重传前按 `config.retry_backoff_ms`（默认 500 ms）顺延，复用 `attempts.not_before`。
* 记账：重传不抹掉代价。`client_total_ms` 仍是**成功那次**的时延；失败尝试的耗时累计在
  `retry_ms_total`、次数在 `retry_count`、原因在 `retry_errors_json`（接口返回 `retry_errors`）。
* 判定口径：**处理总用时 = Σ(client_total_ms) + Σ(retry_ms_total)**，即含重传代价；
  另有"执行总用时"只算成功那次，两个数都给出。
* 额度用尽仍失败则如实记为失败，完成率随之低于 100%——判定项 `complete_gte 100%` 会判不通过，
  平台不会把失败藏起来。
* 只要还有任务没跑完，完成率判定保持「待实测」，不会在运行中显示"不通过"。

## 任务产生窗口

方案要求任务"在 N 分钟内随机产生"。平台按阶段级窗口抽样任务产生时刻，写入
`attempts.not_before`，worker 到点才可领取——所以窗口内任务是**真的分散产生**的，
不是一次性全发。窗口压得越小，任务越挤、越会相互抢占 Pod，测到的主要是排队与干扰；
界面会在到达速率过高时给出提示（见 `planDraft.ts` 的 `windowCaution`）。

### 测量场景

方案按大纲"两台设备各产生任务"，各执行单元（设备 × 任务类型）**并行推进**，
所以方案运行量的是**并发多设备**下的表现。这与「固定套件」在空载节点上逐个任务
测得的差异不是同一个场景，逐类结论可能不同——实测例子：

| 任务类型 | 固定套件（空载、逐个） | 5.4 方案（并发、8 个执行单元） |
|---|---|---|
| 计算类 | 协同 **+29.4%** | 协同 **−169.5%** |
| 诊断类 | 协同 −66.8% | 协同 −91.7% |
| 通信类 | 协同 +73.5% | 协同 **+79.9%** |
| 日常类 | 协同 +35.8% | 协同 **+63.6%** |

计算类在并发下反转，是因为协同要把 3 个分区派发到已经同时被其他单元占用的节点上，
而本地执行把全部计算留在自己 Pod 内；通信/日常类则因为协同的多源并行与作业并发
在并发负载下收益更大。**总用时仍为协同大幅领先（472.5s → 151.6s，+67.9%）**，
因为通信类绝对耗时最大、主导了总量。报告里应写清测的是哪种场景。

### 自定义实验配置

「自定义」卡片给一份可立即运行的模板（1 台设备 × 4 类任务 × 1 个），也可以先在
5.4 / 5.5 上改再下发——任何修改都会作为 `overrides` 传给后端，后端把 overrides
套到方案上生成**不可变快照**存进 `plan_runs.snapshot`，报告可回溯到"当时到底怎么配的"。

## 口径（页面内已注明，勿改）

- **`client_total_ms`** 由站点后端用墙钟在 HTTP 调用外层测量，是**唯一跨模式可比**指标。
- **协同**包含排队等待 `queue_wait_ms`，**本地执行**恒为 0；两者差异同时含「调度开销」与「排队开销」。
- **降级**（琥珀橙徽标）≠ 本地执行：降级额外记录 `degrade_reason`
  （`forced` / `scheduler_unreachable` / `dependency_unhealthy`）。
- 所有聚合旁必须显示样本量 `n`；缺数据一律显示「暂无数据，请先下发测试任务」，
  **不补 0、不推算、不编造图表数据**。

## 对后端返回差异的容错

站点后端与契约文档在某些细节上不同（已在代码中兼容，两者都能读）：

| 位置 | 后端实际返回 | 兼容处理 |
|---|---|---|
| `GET /api/patients` | `{count, patients:[…]}` | 解包信封，也支持裸数组 |
| `GET /api/runs` | spec 字段**平铺**在 run 上，`attempts` 是**数字** | `runSpecLoose()` 统一读取；`asAttemptList()` 判型（否则会对数字调用 `.map()`） |
| `GET /api/runs/{id}` | `{run, progress, summary, attempts:[…]}` | `normalizeRun()` 摊平为 `Run` |
| `GET /api/health` | 降级开关在 `health.config` 里，pods 用 `local_mode_available` | `healthForceDegraded()` / `healthAutoDegrade()`；`local_health.capabilities` 优先 |
| `GET /api/compare` | 聚合嵌在 `client_total_ms:{n,mean,p50,p95,min,max}`，另有 `correctness` | 嵌套与平铺两种都读；`correctness.status` 直接呈现 |
| `GET /api/compare/matrix` | `{rows:[…]}` | 同时接受 `rows` / `matrix` / 裸数组 |
