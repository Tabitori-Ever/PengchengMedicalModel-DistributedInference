01

项目介绍脚本（背下来）

Pitch

60 秒电梯版

“我做的是一个基于 Kubernetes 的云边端协同医疗推理平台：医院（边）和诊所（端）Pod 发起任务， 数据中心（云，node3）承载调度器、推理后端和患者数据库。平台支持四类任务： 诊断（医疗模型前端在院内、后端在云）、计算（多 Pod 分区协同）、 通信（患者库 P2P 云同步与备份）、日常（调度器按节点空闲创建一次性 Job 并回收）。 我的工作覆盖架构演进、调度与路由、性能与稳定性治理、可观测性，以及一个 React 集群编排前端。”

技术栈一句话：K8s (Deployment/Service/Job/RBAC/Affinity) · FastAPI · Redis 优先级队列 · Prometheus/metrics-server · PyTorch 分布式拆分 · React+TS

3 分钟版（背景 → 架构 → 我做的 → 难点与结果）

  • 背景与目标：医疗数据不能出院，但模型后端需要算力 → 把推理拆成“院内前端 + 云端后端”，用 K8s 做编排与资源隔离；后续扩展为四类任务。
  • 架构：三层云/边/端；hospital Pod = 诊断前端 + 通用 worker；clinic Pod = 任务发起与数据 peer；Data Center = scheduler（调度继承）+ medical-server + dc-services（患者库/协同计算/备份）+ Redis。
  • 我做的四件事： ① 调度与路由——把“节点选择”真正落到实体 Pod 服务路由（原实现只在元数据里节点打分，请求仍打到共享 Service）；
    ② 性能治理——定位 /tasks/stats 17 秒的根因（任务把数 MB 输入存 Redis，列表接口全量解析），改为终态剥离 input，降到 ~0.55s；
    ③ 稳定性——定位 scheduler 探针失败→崩溃循环的根因（同步阻塞 + 线程池/GIL 与轮询放大），通过单次 pod list、轻量 summary、降低轮询频率修复；
    ④ 交付——集群编排前端（地图/列表双视图、拖拽改节点、应用/重置）、四类任务可视化与执行轨迹实时地图。
  • 结果：四类任务综合测试 6/6 通过；关键接口 P95 从秒级降到百毫秒级；镜像 3GB→550MB 级别的体积优化；scheduler 0 重启稳定运行；形成 v3.0 正式版与完整版本记录/重构报告。

深挖版：三个“技术决策”讲法

① 为什么调度在云、业务在边？

数据主权（患者数据不出院）决定前端必须落地院内；算力与模型集中决定后端与调度放数据中心。调度器集中=全局资源视图；代价是单点与跨节点 RTT，用“单副本+快速重建+幂等任务”兜底。

② 为什么用 Redis 队列而不是 K8s 原生 Job 做所有任务？

长流水线任务需要优先级/可查询状态/跨 Pod 编排，Redis ZSET 简单可控；日常类才用 K8s Job（一次性、可回收、天然隔离）。混合用法各取所长。

③ 为什么负载从 Prometheus 换成 metrics-server？

调度器需要的是“节点可用量”的快速读数：metrics-server 聚合 API 一次拿全，避免 Prometheus 多查询串联导致的超时/0 值；Prometheus 仍用于历史与告警。

60 秒“难题+成果”话术 · A：17s → 0.55s 的崩溃循环

“我遇到的最大技术难题是：总览页一打开就卡死、30 秒超时，紧接着调度器 Pod 被 liveness 探针反复杀掉，进入崩溃循环，整个平台不可用。 定位靠分段计时——发现只有 /tasks/stats 慢到 17 秒；顺着 Redis 查下去，每条任务记录里都存着数 MB 的医疗输入， 列表/统计接口每次都要全量扫描并解析 JSON；再叠加 5 秒一轮的多接口轮询，线程池被打满，GIL 让健康检查也排不上队，于是探针超时 → Pod 被 kill。 修复三步：任务进终态时剥离 input（存量清理 21 条）、列表接口改单次 pod list 且只返回必要字段、轮询从 5 秒放宽到 8/15 秒。 结果：/tasks/stats 从 17 秒降到 0.55 秒，调度器 0 重启。 我最大的收获是：探针失败往往不是探针的问题，而是主线程被阻塞的可观测信号。”

60 秒“难题+成果”话术 · B：从“假调度”到真路由

“我的最大难题是：调度器看起来一直在工作——策略模块会给节点打分、把结果写进任务记录——但任务实际执行位置和打分结果完全不一致。 定位：对比任务元数据里的 node 与日志里的真实执行 Pod，发现请求永远打到同一个共享 Service，由 K8s 负载均衡随机挑 Pod， 也就是说 policy 只写了元数据、从未影响路由。修复：把调用目标从共享 Service 换成按实体划分的 Service（hospital-a/b、clinic-1/2）， 让策略结果真正决定请求发往哪个实体；后续 v2/v3 的实体化架构都建立在这个认识上。 成果：调度语义与行为一致，任务真正落到目标医院/诊所，并沉淀出一份《任务调度与分发分析》文档。 收获：‘节点选择 ≠ 请求路由’，决策必须落到真实数据路径上，而可观测性（记录实际执行者）是发现假调度的前提。”

用法：A 适合被问“讲讲你排查过的最难的问题 / 做过哪些性能优化”； B 适合被问“你项目里最有技术含量的设计 / 你和 K8s 调度器是什么关系”。 两条都背，开场用一条、追问时用另一条交叉印证（性能问题背后是架构问题，架构问题最终要靠指标验证）。
不要这样讲：“我搭了一个 K8s 集群”就结束。面试官要听的是 你做的取舍、你定位过的真实故障、以及你如何证明修好了。

2.3 五个“可深挖”的故事（面试时按 STAR 讲）

故事 1 · 17 秒的 /tasks/stats 与崩溃循环

S：总览页一打开就卡死、30s 超时，随后 scheduler 被 liveness 杀掉重启。T：恢复可用并找到根因。 A：先用 curl 逐接口计时（stats 17s、tasks 3s），发现任务记录里存着数 MB 医疗输入；读 Pod events 确认探针超时→Killing； 再算并发：每 5s 一轮多接口轮询 + 全量 JSON 解析把线程池打满。 R：终态任务剥离 input（清理存量 21 条）、列表接口单次 pod list、轮询降频，stats 降到 0.55s，scheduler 0 重启。

故事 2 · “调度器看起来在工作，其实没生效”

S：策略打出的节点分与任务实际执行位置不一致。A：读代码发现 policy 只把节点写进 task 元数据，HTTP 仍打到共享 Service（K8s LB 随机）。 R：把路由改为实体 Service（hospital-a/b、clinic-1/2），并在文档中明确“元数据≠路由”，后续 v2/v3 的实体化架构都建立在这个认识上。

故事 3 · Prometheus 负载恒 0 与 30s 超时

S：节点负载环永远 0%，总览偶发超时。A：定位到逐节点、逐指标串行查 Prometheus，任一环节慢就放大； 且监控命名空间/DNS 与实际不一致的风险一直存在。R：改为 metrics-server 聚合 API（一次拿全节点用量）+ allocatable 计算百分比，并加轻量 summary 接口；Prometheus 继续承担历史与告警。

故事 4 · 反亲和 + 滚动更新死锁

S：part2 升级时新 Pod 一直 Pending，旧 Pod 不退出。A：Deployment 设了 required podAntiAffinity（每节点 1 个）+ 默认滚动策略 maxUnavailable≈0， 新 Pod 无处可调度、旧 Pod 又不能先删 → 互相等待。R：显式 maxUnavailable=1, maxSurge=0，并前置预拉镜像；总结为“有反亲和约束时必须算清滚动预算”。

故事 5 · 从“能跑”到“可演示、可解释”（v3.0.4→v3.0.9）

S：功能齐了但演示讲不清。A：把架构拆成逻辑视图（云/边/端/运维分组 + 关系连线）、任务加“执行轨迹地图”（时序高亮、并行步骤同亮、手动下一步/循环演示、图标化与字号层次）。 R：非作者也能在 5 分钟内看懂“哪个任务走了哪条路径、哪一步在并行、慢在哪一段”。

2.4 反复出现的 12 条教训 / 模式（面试时用“我总结过几条规律”收尾）

  • 01 探针/健康检查绝不能和业务负载走同一条路径。业务端口被推理占满时 1 秒超时 → K8s 判死 → 杀 Pod； 改到独立指标端口（9000，由 start_http_server 在独立线程运行、不执行任何推理）后， 压测 10/10 成功、稳定运行 5 分钟+ 0 重启。[版本记录 v13.2]
  • 02 大 payload 不能留在热路径的存储里。数 MB~10MB 的医疗 input 存进 Redis 任务记录， 列表/统计接口每次全量取出解析（实测 17s+/次）；终态剥离 input 后降到 ~0.6s。[版本记录 v2.0.5]
  • 03 有内存上限就有并发上限，必须显式限流。调度器限制 1Gi，4 个 worker + 队列堆积 ≈ 900MB+， 2-3 个并发医疗任务即触发 OOMKilled；把预处理前移到 worker 线程 + threading.Semaphore 后消除。[BUG_ANALYSIS 根因 2 · 版本记录 v13.1]
  • 04 单进程 + 阻塞调用 = 健康检查连带阵亡。uvicorn 单 worker 下，4 个 worker 线程共享 GIL， 序列化大张量时 asyncio event loop 被阻塞，健康检查排队超时，连续 3 次就杀 Pod。[BUG_ANALYSIS 根因 1]
  • 05 没有连接池就会耗光 FD 与端口。requests 每次调用新建 TCP 连接、Redis 每次实例化新建连接， 高并发下 FD 泄漏/连接打满。[BUG_ANALYSIS 根因 3 · 4]
  • 06 软约束不可靠，硬约束必须算清滚动预算。软反亲和实测失效（part1 4 副本里 3 个落 node1）； 而硬反亲和 + 默认滚动策略又造成升级死锁，最后显式 maxUnavailable=1 解套。[架构报告 §实测 · 版本记录 v14]
  • 07 “决策”必须落在数据路径上，元数据不等于行为。节点打分结果只写进 Redis 元数据，HTTP 请求仍打固定 Service， 表现为“调度器在工作但任务不按预期落位”。[TASK_DISPATCH_ANALYSIS §3.1]
  • 08 监控展示 ≠ 业务可编程访问。Grafana 能看到数据，不代表算法模块能取到；需要独立的 Monitoring API 做数据访问层， 让“展示系统”与“决策系统”解耦。[Addtional.txt · 版本记录 v15/v16]
  • 09 预测/模型的口径必须与测量口径一致。预测模型算的是 layer compute，实测却包含序列化+网络+队列+容器开销， 于是出现“通信预测 5ms、实际 918ms”的荒谬偏差。[Addtional.txt §10]
  • 10 量纲与语义细节是真实 bug 来源。K8s 量纲 478Mi 被 int() 解析成 0（内存显示恒 0）； part2 返回 raw logit 被当概率显示成 485.7%。[版本记录 v2.0.1 · v2.0.5]
  • 11 没有分段计时就没有优化方向。只记录整体耗时无法定位慢在哪；改为记录队列/worker(计算·网络)/阶段间/server/流水线/端到端后， 瓶颈一眼可见。[版本记录 v3.0.3]
  • 12 可演示、可解释是交付的一部分。逻辑架构视图 + 执行轨迹地图（时序高亮、并行步骤、手动下一步）让非作者也能在 5 分钟内 看懂“哪个任务走了哪条路径、慢在哪一段”。[版本记录 v3.0.4→v3.0.9]

3.3 关键取舍速答（面试高频追问）

调度器单副本？

当前规模下单副本最简单；风险是 SPOF。方案：无状态化 + 多副本选主（Lease/etcd），任务幂等 + Redis 队列支持重复消费；或把队列换成 K8s 原生 + 控制器。

为什么 Redis 队列，不用 Kafka？

任务量级与时长（秒级~分钟级）不需要高吞吐日志；Redis ZSET 提供优先级与简单运维。代价：持久化与顺序保证弱，用 AOF + 幂等 + 状态机兜底。

患者库为什么是“模拟”？如何演进为真实？

演示阶段用确定性子集 + 分块 + 校验和表达 P2P 语义；真实场景替换为：ORM/数据库 + 变更日志(CDC) + 对象存储分块 + 签名校验 + 版本向量冲突解决。

如何保证“数据不出院”？

架构层：前端只在院内 Pod；网络层：NetworkPolicy 限制出口仅允许到 DC 的中间特征端口；审计层：任务结果记录数据流向与字段。

资源隔离与容量？

requests/limits + QoS；节点超卖用 limit 而非 request 约束；关键组件独立 namespace/优先级（PriorityClass）；后续可上 HPA/VPA 与 Cluster Autoscaler。

如何观测一个任务的慢点？

三层：任务层（分阶段 metrics：队列/worker 计算·网络/阶段间/server/pipeline/e2e）、服务层（直方图 + P95）、节点层（CPU/内存/负载）。先定位段，再下钻到 Pod。

为什么把推理拆成“院内前端 + 云端后端”？拆分点怎么定的？项目

你的调度器具体“调度”了什么？和 K8s 调度器是什么关系？项目+K8s
  • K8s 调度器负责 Pod → Node（资源、亲和、污点）；我的调度器负责 任务 → 实体/Pod 选择 + 流水线编排（优先级、模型约束、转诊、分区、Job 生成）。

任务状态机怎么设计的？失败/超时/重复消费怎么处理？项目
  • 状态：queued → running(stage: scheduler/worker/server/... ) → finished/failed；进度按 stage 映射。

“节点选择≠请求路由”这个问题你是怎么发现并修的？★高频

K8s 01 · Pod 生命周期与探针
✅ k8s 为什么不直接跑容器，而要引入 Pod？Pod
  • Pod 是最小调度单元：调度、扩缩、驱逐的粒度都是 Pod，而不是容器。
  • 同 Pod 内容器共享 Network / UTS / IPC 命名空间，而 USR / MNT / PID 默认隔离，因此可共享 IP、端口与卷。
  • 价值在于 sidecar 模式：日志/代理/注入类容器与主容器同生命周期、同网络栈，一起被调度与被销毁。
✅ Pod 如何“体面终止”？默认宽限期是多少？Pod
  • 删除流程：标记 Terminating → 从 Endpoints 摘除 → 执行 preStop → 向主进程发 SIGTERM → 宽限期到点 SIGKILL。
  • 默认 terminationGracePeriodSeconds=30；宽限期从 preStop 开始计时，两者共用同一预算。
  • 直接拆桥会丢在途请求：长连接服务要么在 preStop 里 sleep 等到连接排空，要么让应用自己处理 SIGTERM 优雅退出。
✅ preStop 执行时间超过宽限期会怎样？Pod
  • 宽限期到点 kubelet 直接强制关闭（SIGKILL），preStop 未执行完就被中断——这是预期行为，不是 bug。
  • 工程含义：preStop 里的等待/排空逻辑必须显著短于宽限期，例如宽限期 60s、preStop 最多等 20s。
  • 只写 sleep 而不真正优雅退出，本质只是“猜一个等待时间”，不如让应用自己处理信号。
✅ 静态 Pod 是什么？哪些组件是静态 Pod？Pod
  • 由 kubelet 直接读取节点上的 manifest 启动，只存在于本节点，API 不能管理、没有探针与健康检查。
  • 我们仍能在 kubectl get pods 里“看见”它，是因为 kubelet 在 API 里建了一个镜像 Pod（mirror pod）。
  • 典型：kube-apiserver、etcd、kube-scheduler、kube-controller-manager——这也是为什么控制面由 kubelet 而非 Deployment 拉起。
✅ Init 容器与普通容器有什么差异？多个 Init 失败会怎样？Pod
  • Init 容器顺序串行执行，必须成功退出才会启动下一个；全部成功后才启动业务容器。
  • 不支持探针与 lifecycle，也不参与 Service Endpoints；失败时按 restartPolicy 重试，Pod 一直卡在 Init:0/2 之类状态。
  • 常见用途：等待依赖（DB/Redis）就绪、修正挂载目录权限、预置配置——比在主容器里写等待脚本更干净。
K8s 02 · Deployment 与滚动更新
✅ Deployment 滚动更新时，ReplicaSet 和 Pod 到底怎么变？Deployment
  • 改 Pod 模板会创建新 ReplicaSet，然后按 maxSurge / maxUnavailable 交替扩容新 RS、缩容旧 RS。
  • 旧 RS 不会被删（受 revisionHistoryLimit 约束），所以 kubectl rollout undo 才能秒回滚。
  • 进度用 kubectl rollout status deployment/<name> 观察；卡住超过 progressDeadlineSeconds 会写入 ProgressDeadlineExceeded 条件。
✅ 上线停滞（rollout 卡住）如何判定与排查？★Deployment
  • 判定：rollout status 长时间不结束、新 RS 期望副本数与就绪数对不上、出现 ProgressDeadlineExceeded。
  • 常见原因清单：镜像拉取失败、ResourceQuota/资源不足、探针一直失败、PVC 未绑定、调度失败（亲和/污点）。
  • 排查顺序：describe pod 看 Events → describe rs 看副本账本 → get events → 必要时先 rollout undo 止血再定位。
✅ StatefulSet 与 Deployment 的本质区别？StatefulSet
  • StatefulSet 提供稳定网络标识（<name>-<ordinal> + Headless Service DNS）、稳定存储（volumeClaimTemplates）与有序启停。
  • 默认逆序滚动更新与逆序缩容，保证主从/分片语义；Deployment 只保证“无状态副本数”。
  • 代价：扩缩与故障恢复更慢（要等旧 Pod 真正删除），且需要应用自身支持身份语义。
✅ 为什么 StatefulSet 需要 volumeClaimTemplates？StatefulSet
  • 每个副本需要独占且与身份绑定的 PVC（data-<name>-0/1/2），不能像 Deployment 那样共用一个卷模板。
  • 缩容时 PVC 不删除，扩回同序号副本会复用原存储，避免数据错配或丢失。
  • 因此清理必须显式做（手动删 PVC），否则会有“孤儿卷”长期占容量——这也是面试常追问的成本点。
✅ 分区滚动更新（partition）有什么用？StatefulSet
  • 设置 updateStrategy.rollingUpdate.partition=N 后，只更新序号 ≥ N 的 Pod，其余保持旧版本。
  • 典型用途：金丝雀/灰度——先升最高序号做验证，再逐步把 partition 降到 0 全量升级。
  • 它与 Deployment 的“副本比例灰度”是两种粒度：StatefulSet 按身份序号，Deployment 按副本百分比。
K8s 03 · Service · Ingress · kube-proxy
✅ kube-proxy 的 iptables 与 IPVS 模式差异？★网络
  • 两者都基于 Netfilter，但设计目标不同：iptables 是防火墙规则链，线性匹配，Service/Endpoints 多时规则数量爆炸、同步与匹配都变慢。
  • IPVS 是为高性能 L4 负载均衡设计的，用 Hash 表查找，配合 ipset 减少规则数，支持 rr/wrr/lc 等调度算法与后端健康检查。
  • 结论：中小集群 iptables 足够；大规模、Service 数量多时优先 IPVS；nftables 是更新的替代方向。
✅ Service 四种类型在自建集群里怎么落地？Service
  • ClusterIP：集群内默认类型，自建集群主力；LoadBalancer 在自建环境需要 MetalLB/云控制器之类实现，否则一直 Pending。
  • NodePort：节点 IP + 30000-32767 静态端口，适合测试与临时暴露（本项目的 monitoring/prediction 就是这样暴露给测试脚本的）。
  • ExternalName：只做 DNS CNAME，指向集群外服务（如托管数据库），没有代理与负载均衡，也没有 Endpoints。
✅ Service 访问不通，定位顺序是什么？★排障
  • 第一步永远看 kubectl get endpoints <svc>：为 <none> 说明 selector 没选中 Pod（或 Pod 未 Ready）。
  • 第二步 kubectl port-forward 直连 Pod 验证容器本身是否在监听；再核对 targetPort 与 containerPort/实际监听地址（必须是 0.0.0.0）。
  • 第三步查代理与网络：kube-proxy 是否正常、CNI 是否健康、NetworkPolicy 是否拦了流量、DNS 是否能解析 FQDN。
✅ Ingress 与 Ingress Controller 是什么关系？Ingress
  • Ingress 只是HTTP/HTTPS 路由规则（host/path → Service 的声明），本身不转发任何流量。
  • 必须部署 Ingress Controller（ingress-nginx、Traefik 等）才会生效；只有 Ingress 对象而没有 Controller 时规则完全无效。
  • 四层（TCP/UDP）与更多协议能力通常靠 CRD 扩展（如 nginx 的 TCP 转发、Gateway API 的 Gateway/HTTPRoute）。
K8s 04 · 网络 CNI · DNS · NetworkPolicy
CNI 到底解决什么问题？CNI
  • 为 Pod 分配 IP、创建 veth/bridge 与路由，实现跨节点 Pod 互通并清理回收网络资源。
  • K8s 只定义接口规范（CNI spec），具体实现有 Flannel / Calico / Cilium 等，所以“换 CNI”等于换整个数据面方案。
  • CNI 出问题的典型后果：Pod 起不来（IP 分配失败）、跨节点不通但同节点正常、域名解析正常但连接超时。
✅ Flannel 与 Calico 怎么选？★网络
  • Flannel：走 Overlay（VXLAN/IPIP），部署简单、心智负担低；代价是封装开销，而且不支持 NetworkPolicy。
  • Calico：基于 L3 BGP 路由转发，通常无封装（性能更好），并且支持 Pod 级 NetworkPolicy。
  • 选型逻辑：只要“能通”且规模小 → Flannel；要网络隔离/多租户/更好性能 → Calico（或 Cilium/eBPF 路线）。
✅ VXLAN 原理与开销？网络
  • 把二层以太帧封装进 UDP 报文（默认端口 4789），在三层网络上打通“大二层”，使 Pod IP 看起来在同一网段。
  • 两个直接代价：一是 MTU 必须下调（常见 1450），否则大包会被分片或丢弃；二是封装/解封装的 CPU 成本。
  • 排查提示：如果小包 ping 通、大包卡住，第一反应就是 MTU/分片问题，而不是“网络全断”。
同节点与跨节点 Pod 通信路径差在哪？网络
  • 同节点：两个 veth pair 挂在同一网桥上，二层直接转发，不经物理网卡、不做 VXLAN 封装，所以延迟与吞吐明显更好。
  • 跨节点：需要走 CNI 维护的路由或 Overlay 封装，经过物理网络 → 这是跨节点通信抖动的主要来源。
  • 调度含义：把频繁交互的两个服务尽量放在同一节点（亲和/拓扑分布），能实打实降低时延。
✅ DNS 解析失败怎么查？★排障
  • 先在 Pod 内验证：nslookup kubernetes.default 或 getent hosts <svc>.<ns>.svc.cluster.local，区分“完全解析不了”与“短名解析不了”。
  • 查 CoreDNS：Pod 是否 Running/Ready、日志有无报错、副本数是否足够（被驱逐会导致间歇性失败）。
  • 再查配置与策略：/etc/resolv.conf 的 ndots/search 域、NetworkPolicy 是否放行 UDP/TCP 53、conntrack 表是否打满。
⚠️ 装了 Calico、NetworkPolicy 却不生效，常见原因？⚠️无来源
  • CNI 本身不支持策略（Flannel 单独用时策略对象会被接受但不起作用），或策略没有落到目标端口的两个方向。
  • 漏了 DNS 出向放行，表现为“网络被隔离后所有域名都解析不了”，很容易误判成 DNS 故障。
  • 这是通用经验、无特定来源；面试时按“我会先确认 CNI 是否支持策略、再确认方向与端口”表述。
K8s 05 · 存储 PV · PVC · CSI
✅ PVC 一直 Pending 的典型原因？★存储
  • StorageClass 的 provisioner 不存在或未就绪；容量/配额不足；访问模式（RWO/RWX）不被后端支持。
  • 云盘/本地卷的可用区与节点不在同一 zone，绑定后也无法挂载。
  • volumeBindingMode: WaitForFirstConsumer 时，PVC 会一直 Pending 直到 Pod 被调度——这是预期，不要误判为故障。
✅ CSI 动态供给与 WaitForFirstConsumer 的意义？存储
  • CSI 用统一接口对接任意存储厂商（云盘/NFS/Ceph 等），K8s 不必内置各家驱动，符合“外部化插件”的设计。
  • 默认 Immediate 模式会先建卷再调度，可能出现“卷在 zone-A、Pod 被调度到 zone-B”的死结。
  • WaitForFirstConsumer 先调度再建卷，让卷落在 Pod 所在 zone，是生产中更稳的默认选择。
✅ PVC 挂载失败（WaitForAttach / Could not mount）怎么查？★排障
  • 先 describe pvc 看绑定与事件，再 describe pod 找 MountVolume 相关事件与具体错误文本。
  • 进容器 df -h、ls /mnt/path 验证是否真挂上；节点侧看 CSI 插件 Pod 状态与 kubelet 日志。
  • 常见根因：zone 不一致、Secret/凭据缺失（Ceph/RBD 常见）、同一 RWO 卷被多节点争用、权限（fsGroup/SELinux）。
⚠️ PV 的回收策略 Delete / Retain 怎么选？⚠️无来源
  • Delete：删 PVC 时自动删后端存储，适合临时/无状态数据；Retain：保留卷，需要人工清理与复用。
  • 数据库、备份类数据一定用 Retain（或至少快照策略），否则一次误删 PVC 就是数据事故。
  • 这是通用实践结论、无特定来源；面试时补一句“我们项目里 Redis 用 hostPath 属于实验级取舍”。
K8s 06 · 调度器与亲和 · 污点 · 拓扑分布
✅ 调度两阶段流程（Filter / Score）？★调度
  • Filter（预选）：剔除不满足资源、亲和/反亲和、污点容忍、卷拓扑等硬条件的节点。
  • Score（优选）：对通过预选的节点按插件加权打分（0-100），取最高分；同分时随机/bind 阶段决胜。
  • 之后还有 Reserve / Permit / Bind 阶段；全部节点被过滤掉时会走 PostFilter 尝试抢占。
✅ Scheduling Framework 有哪些扩展点？★源码
  • QueueSort、PreFilter、Filter、PostFilter（抢占）、PreScore、Score、NormalizeScore、Reserve、Permit、PreBind、Bind、PostBind。
  • 插件通过 KubeSchedulerConfiguration 的 profiles/pluginConfig 启用与调权重，可多 profile 组合不同策略。
  • 面试落点：想加“业务感知调度”不必改 K8s 源码，写一个调度插件就能挂进 Filter/Score 链路。
⚠️ 常用打分插件与权重怎么配？⚠️无来源
  • 常用：NodeResourcesFit（LeastAllocated / MostAllocated / RequestedToCapacityRatio）、NodeAffinity、InterPodAffinity、PodTopologySpread、TaintToleration、ImageLocality。
  • NodeResourcesFit 默认权重 1，可在 pluginConfig 改权重与打分策略；LeastAllocated 更均衡、MostAllocated 更“装箱省资源”。
  • 该项为通用知识、无特定来源；说的时候强调“先明确目标是均衡还是碎片最少，再调权重”。
抢占（Preemption）是怎么工作的？调度
  • 高优先级 Pod 调度失败时，PostFilter 在候选节点上寻找可驱逐的低优先级 Pod，驱逐后重新入队调度。
  • 受 PodDisruptionBudget 与 preemptionPolicy 约束；受害者是“刚好够用”的最小集合，而不是随便删。
  • 工程含义：PriorityClass 配错会导致“低优先级任务被反复驱逐”，任务型集群必须显式设计优先级层级。
节点 NotReady 之后，上面的 Pod 会怎样？节点
  • 新 Pod 不再调度到该节点；节点上的 Pod 因 node lease 超时被标记为 NotReady/Unknown。
  • Deployment 会触发重建（在其他节点拉起新副本）；StatefulSet 必须等原 Pod 真正删除才能重建，因此多副本会短暂不可用。
  • 缓解手段：node-monitor-grace-period 与容忍时间调优、PDB、以及把有状态负载做到能快速故障转移。
K8s 07 · 资源 requests · limits · QoS
内存超限与 CPU 超限的表现差异？★资源
  • CPU 是可压缩资源：超限只是被 CFS 限流（throttle），表现为延迟变高，可用 container_cpu_cfs_throttled_periods_total 观察。
  • 内存是不可压缩资源：cgroup 超限直接 OOMKilled，退出码 137，Pod 进入 CrashLoopBackOff。
  • 所以“CPU 打得满”和“内存超了”是两类完全不同的故障：前者要调权重/限流策略，后者要查泄漏与 limit 是否过小。
怎么防止 noisy neighbor（邻居干扰）？资源
  • 关键服务设 Guaranteed（requests==limits）；非关键负载用 limits 约束，避免抢占式消耗。
  • 用 LimitRange 兜底默认 requests/limits，用 ResourceQuota 限制命名空间总量，防止单个团队吃满集群。
  • 极致场景再用 cpu-manager 静态绑核（cpuset）与内存大页，让关键负载独占 CPU 核。
节点内存不足时，kubelet 按什么顺序驱逐 Pod？资源
  • 依据 kubelet 的软/硬驱逐阈值（memory.available、nodefs 等），按 QoS 与超用量排序。
  • QoS 顺序：BestEffort → Burstable → Guaranteed；同类中优先驱逐“用量超出 requests 最多”的 Pod。
  • 因此设 requests 不只是为了调度，也是被驱逐顺位的保护；同时用 system-reserved/kube-reserved 保住系统进程。
K8s 08 · RBAC 与安全
✅ RBAC 的授权流程与“只增不减”是什么意思？★安全
  • 请求先认证（Authentication）再鉴权（Authorization）：Subject（User/Group/ServiceAccount）→ Role/ClusterRole → Binding。
  • 规则是白名单、只增不减：没有 deny 规则，匹配到任意一条 allow 即通过；因此“多绑一个 Role”就等于永久放权。
  • 排查利器：kubectl auth can-i <verb> <resource> -n <ns> --as=system:serviceaccount:<ns>:<sa>。
Role 与 ClusterRole 什么时候用哪个？安全
  • Role 只作用于单一命名空间（配合 RoleBinding）；ClusterRole 用于集群级资源（nodes、PV、CRD）或需要跨命名空间复用。
  • 常见组合：定义 ClusterRole 描述权限，再用 RoleBinding 把它绑到某个命名空间的 SA，做到“权限模板 + 命名空间隔离”。
  • 反面案例：直接给 CI/CD 或调度器绑 cluster-admin，一旦被利用就是集群级失陷。
✅ default ServiceAccount 有什么风险？★安全
  • Pod 默认挂载 default SA 的 token；如果该 SA 被授予过宽权限，任何一个被攻破的 Pod 都能横向提权。
  • 缓解：automountServiceAccountToken: false（不需要访问 API 的 Pod 一律关闭）、为应用建专用最小权限 SA。
  • 更彻底：用 TokenRequest 拿短期、受众受限的 token，而不是长期有效的 Secret 式 token。
⚠️ 怎么快速验证一个 SA 的权限边界？⚠️无来源
  • kubectl auth can-i --list --as=system:serviceaccount:<ns>:<sa> 列出全部允许项，比逐个动词试快得多。
  • 再结合实际调用（例如让 Pod 内的 client 去 list deployments）验证是否被拒绝，避免“看起来有权限其实绑定没生效”。
  • 属通用操作经验、无特定来源；本项目里的做法是：只给调度器 default 命名空间的 deployments/services/jobs/pods/log 权限。
K8s 09 · 控制面与 etcd
✅ etcd 的性能与容量注意点？★etcd
  • etcd 是唯一持久化数据源，强一致（Raft）：每次写都要多数派确认，因此磁盘 fsync 延迟直接决定 apiserver 写延迟。
  • 建议 SSD；控制 --quota-backend-bytes（默认 2GB）；定期 defrag 回收空间；避免高频写入大对象（超大 ConfigMap/CR status）。
  • watch 数量过多会显著推高内存；大规模场景要控制 informer 数量与对象体量。
✅ apiserver 变慢，怎么判断是不是 etcd 的问题？etcd
  • 看 etcd 自身指标：backend_commit_duration_seconds、wal_fsync_duration_seconds、mvcc db size、leader 切换次数、磁盘 IO。
  • 再对比 apiserver 各 verb/resource 的 latency 直方图：如果只有写类 verb 慢，且 etcd commit/fsync 同步升高，基本可定位到 etcd 与磁盘。
  • 常见诱因：磁盘抖动、大对象写入（如数 MB 状态）、list 全量读、quota 接近上限触发告警式 compaction。
✅ 控制面高可用要注意什么？控制面
  • 多 master + 多 etcd 成员，成员数取奇数（3 或 5）以保证多数派；前置 LB 统一暴露 6443。
  • etcd 与 apiserver 尽量同机房低延迟部署——Raft 对 RTT 极其敏感，跨机房会放大写延迟。
  • 必须有定期快照备份，并且演练过恢复：没演练过的备份等于没有备份。
etcd 备份与恢复怎么演练？★控制面
  • 用 etcdctl snapshot save 定期导出快照，并记录集群版本/成员列表，恢复时保持一致以免版本不兼容。
  • 演练要点：在隔离环境用 snapshot restore 起单节点，验证关键对象（Deployment/Service/CRD）是否完整。
  • 指标口径：RTO（多久恢复）与 RPO（丢多少数据）必须写下来，否则“有备份”无法回答面试追问。
K8s 10 · 监控与可观测
✅ Prometheus 的拉取模型与生态？★监控
  • 主动 pull：按服务发现抓取目标的 /metrics，天然适合“目标是否存活”的判断；Pushgateway 只用于短生命周期任务。
  • 生态分工：Prometheus 存储与查询、Alertmanager 做分组/抑制/静默、Grafana 做可视化。
  • 所以 /metrics 是给 Prometheus 拉取的，不是给业务调用的 API——本项目 v15/v16 的“Grafana 看得到、程序取不到”就是这个边界。
四种指标类型怎么选（Histogram vs Summary）？监控
  • Counter（只增，如请求总数）、Gauge（可增减，如内存/队列长度）、Histogram（服务端分桶，可聚合算分位）、Summary（客户端算分位）。
  • Histogram 可跨实例聚合（sum 后再算分位），是 P95/P99 与 SLO 告警的首选；Summary 分位无法跨实例聚合。
  • Histogram 的成本在桶边界设计：桶选得不合理，要么精度不够，要么时间序列基数爆炸。
⚠️ K8s 常用告警怎么设？⚠️无来源
  • 以 SLO 为锚：Pod 重启率、container_memory_working_set_bytes 接近 limit、节点磁盘/inode 水位、apiserver 5xx 与 P99 延迟。
  • 再加等得起的信号：etcd fsync 延迟、PDB 违反次数、队列积压与任务排队时长。
  • 本条为通用经验、无特定来源；实践上用多窗口 burn rate 告警，避免单窗口抖动造成“告警疲劳”。
⚠️ 为什么高基数标签会拖垮 Prometheus？⚠️无来源
  • 时间序列数 ≈ 指标名 × 标签取值组合：把 task_id、Pod 名、患者 ID 之类放进标签，序列数会随请求量线性膨胀。
  • 后果：内存与磁盘暴涨、查询变慢、甚至 Prometheus 被压死——本项目 v11 就明确避开“每请求一条 time series”。
  • 属通用经验、无特定来源（本项目版本记录 v11 有同类结论）；正确做法是高基数维度只进日志/追踪，不进标签。
K8s 11 · Job · CronJob · Operator · CRD
✅ CRD 与 Operator 是什么关系？★Operator
  • CRD 只定义新的 API 类型与 schema（“能存什么对象”）；Operator = CRD + Controller，用调谐循环把期望状态落地。
  • Operator 的价值是把“运维知识”编码成控制器：扩缩、备份、故障恢复都不再依赖人执行脚本。
  • 本项目对应关系：现在的脚本化调度/集群编辑可以收敛成“Mission CRD + reconcile”，这正是面试加分表达。
✅ Reconcile 的设计要点？Operator
  • 必须幂等、无状态（状态存 etcd）、基于 level-based 而非 edge-based：每次都对账“当前状态 vs 期望状态”。
  • 配套机制：finalizer 做外部资源清理、Status conditions 表达阶段、ownerReference 做级联回收、RateLimiter 做退避重试。
  • 反模式：把业务状态藏在控制器内存里、靠事件顺序假设、reconcile 里做长耗时阻塞操作。
✅ 为什么 List 大量 CR 会超时？Operator
  • apiserver 需要序列化整个对象集合，etcd 需要读全量，体量随对象数量与单对象大小同时放大。
  • 正确姿势：用 watch + informer 本地缓存 代替轮询全量 list，分页用 limit/continue，必要时按 label/field selector 收窄。
  • 治理手段：精简 status（不要把大数组写进 status）、拆分分片 CR、设置合理的 resync 周期。
⚠️ Job 的 parallelism / completions / backoffLimit 怎么配？⚠️无来源
  • completions 是需要的成功次数，parallelism 是同时可跑几个 Pod；backoffLimit 控制失败重试上限。
  • 配合 activeDeadlineSeconds 控超时、ttlSecondsAfterFinished 自动清理，避免 Job 与 Pod 长期堆积。
  • 属通用知识、无特定来源；本项目 routine 任务用的是“创建 Job → 轮询 → 读日志解析 JSON → 删除 Job”闭环。
⚠️ CronJob 的并发与“错过调度”怎么处理？⚠️无来源
  • concurrencyPolicy：Allow（默认）/ Forbid（上一次没跑完就跳过）/ Replace（替换上一次）。
  • startingDeadlineSeconds 决定“错过多久之内还补跑”，设置过小会静默丢任务，过大又可能集中补跑压垮集群。
  • 属通用知识、无特定来源；生产建议 Forbid + 告警“该跑没跑”，而不是默默 Replace。
K8s 12 · 容器运行时与节点运维
✅ 容器隔离的原理（namespace + cgroups）？★运行时
  • Linux Namespace 做视图隔离：PID/NET/MNT/UTS/IPC/USER 各自看到独立的进程、网络、挂载与主机名。
  • cgroups 做资源限制与统计：CPU（CFS 配额/权重）、内存（limit→OOMKill）、IO、PID 数量。
  • 因此“容器不是轻量虚拟机”：共享内核，隔离强度弱于 VM；这是多租户安全讨论的起点（gVisor/Kata 就是补这块）。
kubelet 与 containerd 的调用链？运行时
  • kubelet → CRI（gRPC）→ containerd（cri 插件）→ containerd-shim → runc → 容器进程。
  • shim 的作用：让容器进程与 containerd 解耦，containerd 重启不影响运行中的容器。
  • 调试入口 crictl ps / crictl logs / crictl pods，是节点侧排障时比 docker 更贴近真实运行时的一层。
✅ Docker 与 containerd 是什么关系？运行时
  • Docker 曾内置 containerd 作为运行时内核；K8s 1.24 起移除 dockershim，改用 CRI 直连 containerd/CRI-O。
  • 设计意图：镜像构建（docker build）与运行时（containerd）解耦，集群不再依赖 Docker 这个“大而全”的守护进程。
  • 迁移影响：节点排障命令从 docker ps 换成 crictl/nerdctl，镜像命名与命名空间也略有差异。
节点层排障的命令清单？★排障
  • kubectl describe node 看 Conditions、Allocated resources 与 Events；kubectl top node/pod 看实时用量。
  • 节点上：journalctl -u kubelet -f、systemctl status containerd、crictl ps/pods/logs。
  • 资源侧：df -h（ephemeral-storage/镜像/日志）、free -m、ss/iptables -L、以及到 apiserver 的网络连通性。
K8s 13 · 高频源码级追问
✅ kubectl 更新 Pod 配置时，Kubernetes 内部发生了什么？★源码
  • kubectl 把改动转成 API 请求 → apiserver 认证/鉴权/准入（Mutating→Validating）→ 写 etcd。
  • controller-manager 的 Deployment/RS 控制器通过 watch 感知模板变化，创建新 RS 与新 Pod；scheduler 绑定节点；kubelet 拉镜像起容器。
  • 关键点：Pod 的 spec 绝大部分字段不可变，所以“改配置”实际上是新建 Pod 而非原地修改——能原地改的只有少数（如 image、activeDeadlineSeconds、tolerations 的部分场景）。
✅ 为什么控制器要 level-based，而不是 edge-based？★源码
  • 事件可能丢失、重复、乱序；只有“对账当前状态与期望状态”才能自我修复（自愈来自反复对账，而不是事件可靠性）。
  • 因此 reconcile 要求幂等：同一对象被处理 N 次，结果必须一致。
  • 工程延伸：写业务调度器同样应“可重入、可重放”，本项目用任务状态机 + 幂等任务 id 表达同一思想。
✅ 为什么用 informer/watch 而不是轮询？源码
  • List+Watch 建立本地缓存（informer store），事件驱动更新，避免高频全量 list 压垮 apiserver 与 etcd。
  • 配合 resourceVersion 做增量、workqueue 做去重与速率限制，才能在大集群里稳定运行。
  • 反面：控制器里写 for { list(); sleep(5) } 是典型反模式——本项目排障时也遇到过“轮询放大”导致探针超时。
⚠️ 探针为什么由 kubelet 直连 Pod IP，而不走 Service？⚠️无来源
  • 探针语义是“检查这个容器是否健康”，kubelet 直接访问 Pod IP + 容器端口，避免 Service 负载均衡把请求转给别的副本造成误判。
  • 这也解释了 readiness 与 Endpoints 的闭环：readiness 失败 → kubelet 上报 → Endpoints 摘除，流量才不再进来。
  • 本条为机制推断、无特定来源；面试时可以说“从现象看是直连 Pod IP，Service 只服务于集群内客户端流量”。
⚠️ 删掉一个 Pod 后为什么又自动出现一个？⚠️无来源
  • 因为 Pod 有 ownerReference 指向 ReplicaSet，而 RS 控制器持续对账“期望副本数 vs 实际数”，发现缺一个就再建一个。
  • 只删 Pod 是“治标”，要真正下线应改 Deployment 模板/副本数或删除上层对象（级联回收）。
  • 属机制推断、无特定来源；这条常被用来区分“会敲命令”和“理解控制器模型”。
B. K8s 核心（自测用，答案要点）
Pod 的生命周期阶段与常见异常状态？基础
  • 阶段：Pending → Running → Succeeded/Failed；Unknown 表示与 kubelet 失联。
  • 异常：Pending（资源/亲和/污点/未绑定 PVC）、ContainerCreating（拉镜像/挂载）、CrashLoopBackOff（进程反复退出/探针失败）、ImagePullBackOff、OOMKilled（超 limit）、Evicted（节点压力）。
  • 排查：describe pod 看 Events → logs --previous → exec 复查配置。
liveness / readiness / startup 探针的区别与常见坑？★基础
  • liveness 失败=重启容器；readiness 失败=从 Service Endpoints 摘除；startup 用于慢启动，成功后其余探针才生效。
  • 坑：探针打业务端口被阻塞请求拖超时（本项目遇到的崩溃循环）；探针路径依赖下游服务；initialDelay 不足导致误杀。
  • 实践：探针走轻量 endpoint 或独立管理端口，超时与 failureThreshold 留余量，用 startupProbe 保护冷启动。
requests / limits 与 QoS 等级？★基础
  • Guaranteed：所有容器 requests=limits；Burstable：设了 requests 但不等于 limits；BestEffort：都没设。
  • 驱逐优先级：BestEffort → Burstable → Guaranteed；CPU 超限被限流（throttle），内存超限被 OOMKill。
  • 调度只看 requests；节点可超卖（sum(limits) > allocatable）。
Service 类型与 kube-proxy 转发模式？基础
  • ClusterIP（集群内）/ NodePort（节点端口）/ LoadBalancer / ExternalName；Headless（无 ClusterIP，直接解析到 Pod IP）。
  • iptables 模式：随机等概率 DNAT；IPVS 模式：支持 rr/wrr/lc 等调度算法与更好扩展性；nftables 是更新的方向。
  • 会话保持用 sessionAffinity；跨命名空间访问用 FQDN。
Deployment 滚动更新参数与回滚？★基础
  • maxSurge/maxUnavailable 决定新旧副本配比；revisionHistoryLimit 保留历史 RS；kubectl rollout undo 回滚。
  • 进度判定看 conditions 与 rollout status；progressDeadlineSeconds 控制“卡住”判定。
  • 与反亲和/PDB 交互时要预留滚动预算（本项目死锁案例）。
节点亲和 / 污点容忍 / 拓扑分布怎么选？★调度
  • nodeAffinity：硬约束（required）用于架构性限制（如 role=edge），软约束（preferred）用于偏好。
  • taint/toleration：把节点“推开”普通 Pod（专用节点）；GPU/控制面无调度常用。
  • podAntiAffinity / topologySpreadConstraints：控制副本分散；required 用于强隔离，soft 用于尽量均衡（避免死锁）。
存储：PV/PVC/StorageClass/CSI 与常见问题？基础
  • PVC 声明需求 → StorageClass 动态供给 PV → CSI 驱动落地（云盘/NFS/Ceph）。
  • 访问模式 RWO/ROX/RWX；hostPath 仅适合单节点/实验（本项目 Redis 用 hostPath 的取舍）。
  • 常见问题：Pending 未绑定、挂载失败、容量不足、回收策略 Delete/Retain 差异。
RBAC 三要素与最小权限实践？★安全
  • Subject（User/Group/ServiceAccount）+ Role/ClusterRole + RoleBinding/ClusterRoleBinding。
  • 实践：按命名空间 + 具体 resource/verb 授权；避免 cluster-admin；用 kubectl auth can-i 验证。
  • 本项目给 scheduler 授权 default 命名空间的 deployments/services/jobs/pods/log，仅够集群编辑器与日常 Job 使用。
网络：CNI/Flannel、DNS 解析链、常见不通怎么查？★排障
  • Flannel 常见 host-gw/VXLAN；跨节点 Pod IP 由 CNI 分配，路由由 CNI/节点维护。
  • DNS：Pod 的 /etc/resolv.conf → CoreDNS Service → 上游；FQDN 形式 svc.ns.svc.cluster.local。
  • 排查序：Pod 内 ping/curl Service → 看 Endpoints 是否为空 → CoreDNS 日志 → 网络策略/iptables。
Job / CronJob 与一次性 Pod 的正确姿势？项目相关
  • restartPolicy=Never/OnFailure、backoffLimit、activeDeadlineSeconds、ttlSecondsAfterFinished 自动清理。
  • 并发策略（Allow/Forbid/Replace）；完成判定看 status.succeeded/failed。
  • 本项目 routine 任务：调度器创建 Job → 轮询 → 读 pod 日志解析 JSON → 删除 Job（含失败/超时清理）。
控制面组件职责与 etcd 的注意事项？基础
  • apiserver（唯一入口/鉴权/校验/准入）、etcd（唯一数据源）、scheduler（绑定 Pod 到 Node）、controller-manager（副本/端点/节点控制器）。
  • etcd：奇数副本、低延迟磁盘（fsync 敏感）、定期快照备份、watch 事件量控制。
HPA / VPA / Cluster Autoscaler 区别？★扩展
  • HPA：按指标（CPU/内存/自定义如队列深度）调副本数；VPA：调 requests/limits（多为推荐模式）；CA：节点不够时加节点。
  • 关键：自定义指标（队列长度）常比 CPU 更适合任务型负载；需注意冷启动与指标延迟导致震荡。

LRU 缓存（container/list + map）Go 
type entry struct { k, v int }

type LRU struct {
    cap  int
    ll   *list.List               // front = 最近使用
    m    map[int]*list.Element
}

func NewLRU(c int) *LRU {
    return &LRU{cap: c, ll: list.New(), m: map[int]*list.Element{}}
}

func (c *LRU) Get(k int) int {
    if e, ok := c.m[k]; ok {
        c.ll.MoveToFront(e)
        return e.Value.(entry).v
    }
    return -1
}

func (c *LRU) Put(k, v int) {
    if e, ok := c.m[k]; ok {
        e.Value = entry{k, v}
        c.ll.MoveToFront(e)
        return
    }
    e := c.ll.PushFront(entry{k, v})
    c.m[k] = e
    if c.ll.Len() > c.cap {
        last := c.ll.Back()
        delete(c.m, last.Value.(entry).k)
        c.ll.Remove(last)
    }
}

并发版：加 sync.Mutex，或分片（sharded LRU）降低锁竞争；面试可主动提“读写锁不适用（写频繁）+ 分片”。

并发 Worker Pool（context 取消 + 优雅退出 + panic 兜底）Go 
func Run(ctx context.Context, jobs <-chan Job, workers int) {
    var wg sync.WaitGroup
    for i := 0; i < workers; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for {
                select {
                case <-ctx.Done():
                    return
                case j, ok := <-jobs:
                    if !ok { return }
                    func() {
                        defer func() { if r := recover(); r != nil { log.Printf("job panic: %v", r) } }()
                        j.Do(ctx)
                    }()
                }
            }
        }()
    }
    wg.Wait()
}

要点：谁关闭 channel（发送方关闭）、ctx 取消要能打断阻塞、panic 不能杀死进程、WaitGroup 与 goroutine 泄漏要说清。

type Limiter struct {

    rate     float64 // 每秒补充

}

func (l *Limiter) Allow() bool {
    l.mu.Lock(); defer l.mu.Unlock()
    now := time.Now()
    l.tokens = math.Min(l.burst, l.tokens+now.Sub(l.last).Seconds()*l.rate)
    l.last = now

    return false
}

TopK（小顶堆）/ 数据流中位数（双堆）Go/Py 
// Go: 用 container/heap 维护大小为 k 的小顶堆，O(n log k)
type IntHeap []int
func (h IntHeap) Len() int            { return len(h) }
func (h IntHeap) Less(i, j int) bool { return h[i] < h[j] }
func (h IntHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *IntHeap) Push(x any)     { *h = append(*h, x.(int)) }
func (h *IntHeap) Pop() any {
    o := *h; n := len(o) - 1; v := o[n]; *h = o[:n]; return v
}

func TopK(nums []int, k int) []int {
    h := &IntHeap{}
    for _, v := range nums {
        heap.Push(h, v)
        if h.Len() > k { heap.Pop(h) }
    }
    return *h
}

双堆中位数：大顶堆存较小半、小顶堆存较大半，保持 size 差 ≤1，插入 O(log n)、取中位数 O(1)。

func Topo(tasks []string, deps map[string][]string) ([]string, bool) {
    indeg := map[string]int{}
    for _, t := range tasks { indeg[t] = 0 }
    for t, ds := range deps {
        for _, d := range ds { _ = t; indeg[t]++ ; _ = d }
        // 注意方向：d 是 t 的前置，则 indeg[t]++
    }
    q := []string{}
    for _, t := range tasks { if indeg[t] == 0 { q = append(q, t) } }
    out := []string{}
    for len(q) > 0 {
        t := q[0]; q = q[1:]
        out = append(out, t)
        for _, nxt := range deps[t] {
            indeg[nxt]--
            if indeg[nxt] == 0 { q = append(q, nxt) }
        }
    }
    return out, len(out) == len(tasks)
}

★ 单调队列 · 滑动窗口最大值（Go + Python）——MiniMax 面经原题★Go/Py 
// 返回每个长度为 k 的窗口的最大值；单调队列，时间 O(n)、空间 O(k)
func MaxSlidingWindow(nums []int, k int) []int {
    if len(nums) == 0 || k <= 0 { return nil }
    dq := make([]int, 0, k)          // 存下标，nums[dq] 从队首到队尾单调递减
    res := make([]int, 0, len(nums)-k+1)
    for i, v := range nums {
        for len(dq) > 0 && nums[dq[len(dq)-1]] <= v { // 队尾比新元素小 → 永远不可能成为最大值
            dq = dq[:len(dq)-1]
        }
        dq = append(dq, i)
        if dq[0] <= i-k { dq = dq[1:] }     // 队首已滑出窗口
        if i >= k-1 { res = append(res, nums[dq[0]]) }
    }
    return res
}

# Python：collections.deque 写同一个逻辑，面试更快
from collections import deque
def max_sliding_window(nums, k):
    dq, out = deque(), []                  # dq 存下标，值单调递减
    for i, v in enumerate(nums):
        while dq and nums[dq[-1]] <= v: dq.pop()
        dq.append(i)
        if dq[0] <= i - k: dq.popleft()
        if i >= k - 1: out.append(nums[dq[0]])
    return out

要点与追问：① 队列里存下标而不是值（否则无法判断是否滑出窗口）；② 每个元素最多进出队一次，所以是 O(n) 而非 O(nk)； ③ 边界：k>len(nums)、k==1、k<=0、空数组；④ 同族变形：窗口最小值（改为递增队列）、 窗口内第一个更大元素、队列的最大值（LeetCode 剑指 offer 59）。

二分查找边界模板（lower_bound / upper_bound）Go 
// 第一个 >= target 的下标；全小于 target 时返回 len(a)
func LowerBound(a []int, target int) int {
    lo, hi := 0, len(a)               // 循环不变量：答案一定在 [lo, hi] 内
    for lo < hi {
        mid := lo + (hi-lo)/2          // 防 (lo+hi) 溢出
        if a[mid] < target { lo = mid + 1 } else { hi = mid }
    }
    return lo
}

// 第一个 > target 的下标（upper_bound）
func UpperBound(a []int, target int) int {
    lo, hi := 0, len(a)
    for lo < hi {
        mid := lo + (hi-lo)/2
        if a[mid] <= target { lo = mid + 1 } else { hi = mid }
    }
    return lo
}

要点：① 统一成“左闭右开 + 返回插入位置”，比写 while lo<=hi 的三种变体更不容易错； ② 出现次数 = UpperBound - LowerBound；③ 变形：搜索旋转排序数组、找峰值、二分答案（求最小可行值，如“最小容量”类题）； ④ 先问清“有序是否含重复、找不到返回什么”。

并查集（Union-Find：路径压缩 + 按秩合并）Go 
type DSU struct{ p, rank []int }

func NewDSU(n int) *DSU {
    d := &DSU{p: make([]int, n), rank: make([]int, n)}
    for i := range d.p { d.p[i] = i }
    return d
}

func (d *DSU) Find(x int) int {
    for d.p[x] != x {
        d.p[x] = d.p[d.p[x]]     // 路径压缩：隔代指向祖父
        x = d.p[x]
    }
    return x
}

func (d *DSU) Union(a, b int) bool {
    ra, rb := d.Find(a), d.Find(b)
    if ra == rb { return false }      // 已连通 → 这条边构成环
    if d.rank[ra] < d.rank[rb] { ra, rb = rb, ra }
    d.p[rb] = ra
    if d.rank[ra] == d.rank[rb] { d.rank[ra]++ }
    return true
}

要点：① 均摊复杂度近似 O(α(n))，几乎常数；② 统计连通分量数 = 所有满足 Find(i)==i 的个数； ③ 场景落到 K8s 语境：判断节点/集群分组、检测依赖成环、Kruskal 最小生成树；④ 需按维度分组时用 map[string]int 做名字到编号的映射。

合并区间 / 排序扫描模板Go 
import "sort"

func Merge(intervals [][]int) [][]int {
    if len(intervals) == 0 { return nil }
    sort.Slice(intervals, func(i, j int) bool { return intervals[i][0] < intervals[j][0] })
    res := [][]int{intervals[0]}
    for _, cur := range intervals[1:] {
        last := res[len(res)-1]
        if cur[0] <= last[1] {              // 相接也算重叠，按题意确认用 <= 还是 <
            if cur[1] > last[1] { res[len(res)-1][1] = cur[1] }
        } else {
            res = append(res, cur)
        }
    }
    return res
}

要点：① 排序后只需和“结果集最后一个区间”比较，O(n log n) 由排序决定；② 边界：空输入、单区间、完全包含、逆序输入； ③ 变形：插入区间（先二分定位再合并）、会议室数量/最大重叠数（最小堆或差分数组）、区间调度（按右端点贪心）。 ④ 工程映射：合并任务的时间窗、任务批次合并下发。

def run_all(items, fn, workers=8):
